# v1.4.0 Startup Pipeline v2

## Measured startup boundaries

`StartupTiming` records elapsed milliseconds and managed thread ID for the App constructor, launch entry, MainWindow construction, XAML initialization, root content, language/theme readiness, activation, main-page Loaded, and background completion. It emits timing diagnostics only in Debug builds and records the final safe timing fields to the local JSONL logger.

## Pipeline classification

- Critical / before UI: first-run decision, settings load, persisted language application, MainWindow construction, and theme application.
- First frame: RootFrame navigation, main-page Loaded, startup overlay completion, and `Window.Activate()`.
- After first frame: notification reconciliation and first-run guide decision.
- Background: infrastructure directory creation, log writing, and rolling retention. No update check or network operation is part of startup.

The pipeline is one-shot and catches background failures. Retention runs on the thread pool and does not block the first usable frame. No artificial delay or Splash asset change was introduced.

## Before / after audit

Before this phase, post-activation work was an unguarded dispatcher callback that synchronously created directories, ran retention, and awaited notification reconciliation. There was no timing stream and a notification exception could escape the callback.

After this phase, post-activation work is coordinated by `StartupPipeline`, timing points are observable, retention is off the UI thread, and notification/maintenance failures are local-only diagnostics. Distribution detection and update services remain outside the critical startup path.

Real cold-launch median measurements require manual Windows launch acceptance on the target machine; this code provides the required five-run measurement points without changing the normal UI with a diagnostics console. The known Splash logo rendering issue remains deferred.
