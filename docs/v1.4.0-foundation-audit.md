# UrbanPlanToolbox v1.4.0 Foundation Update

## Phase 0 audit

This audit is based on the current `main` worktree on 2026-08-07. Existing
uncommitted v1.3.2 changes were preserved and are not part of this audit's
implementation scope.

### Dependency map

```text
App.OnLaunched
  -> FirstRunExperienceService / SettingsService / LocalizationService
  -> MainWindow
       -> PrimaryNavigation + ShellNavigationState
       -> Home/Project pages -> ProjectStorageService -> JsonDataStorage
       -> Tool category pages -> ToolCategoryBrowser -> ToolRegistry
       -> Search page -> ToolSearchService -> ToolRegistry
       -> Favorites -> FavoriteToolsService -> SettingsService
       -> About -> AppUpdateServiceFactory -> channel-specific update service
  -> deferred MilestoneReminderService -> ProjectStorageService + notifications
```

### Findings

| Question | Current state | v1.4 implication |
|---|---|---|
| A. Adding a tool | Normally one `ToolDefinition` entry, one `ToolIds` constant, one page, three localized resource groups, and tests. Category pages, search, favorites and navigation consume the registry. | Keep the registry as the single metadata source; add explicit capability/visibility flags. |
| B. Tool metadata | `Services/ToolRegistry.cs` + `Models/Tools/ToolDefinition.cs` hold ID, resource keys, category, icon, page type, sort and search metadata. Category definitions are in `Models/Tools/ToolCategory.cs`; favorites are persisted as IDs in `AppSettings`; localization is in `Strings/*/Resources.resw`. | Remaining duplication is category catalog and resource files, not per-page tool lists. Do not create a second descriptor model. |
| C. Local data | `JsonDataStorage` envelopes for tool/project/checklist data; `ProjectStorageService` project index and project files containing archive state, Todo, planning snapshots and work-folder references; `SettingsService` settings JSON containing favorites; `BackupDataService` portable ZIP; first-run and tool-specific JSON stores. | Use the existing envelope and path provider; migrate per storage boundary. |
| D. Formal version fields | Yes for JSON envelopes (`schemaVersion`), project schema (currently 3), checklist schema, settings schema, and backup manifest (`BackupFormatVersion`, currently 1). | Normalize names and introduce explicit backup format v2 only with backward read compatibility. |
| E. Old data compatibility | `DataMigrationRunner` executes sequential `IDataMigration` steps on a deep clone; `JsonDataStorage` writes only after validation and keeps a backup. Project migrations currently cover 1→2→3. | Extend the existing chain; do not scatter more legacy checks through domain code. |
| F. Import/export format | Backup ZIP has a manifest, version, limits, hashes, staging extraction, pre-import backup and rollback. | Rename/add v2 manifest fields by compatibility-aware deserialization; preserve v1 imports. |
| G. Settings | Central `SettingsService` exists, but settings use public strings/enums and `Load` normalizes only by fallback. `MilestoneReminderService` also performs a legacy setting migration. | Add centralized keys, typed normalization and tests without moving `settings.json`. |
| H. GitHub/Store coupling | `AppDistributionChannelService` detects exact Store identity. `AppUpdateServiceFactory` selects `StoreAppUpdateService` or `GitHubAppUpdateService`; UI still receives update behavior through the view model. | Extract a small channel capability object/factory only where it reduces UI branching; preserve identity constants and update paths. |
| I. Startup I/O | Settings load is synchronous before window creation. Infrastructure setup and reminder refresh are deferred through `DispatcherQueue`; project reads and notification scheduling are asynchronous. | Keep only settings/language/theme/root before first frame; add stage timing and move safe maintenance after first frame. |
| J. UI-thread initialization | `SettingsService.Load`, theme/language application and window construction occur before activation. Reminder work is deferred. `MilestoneReminderService.ClearOwnedSchedules` has a synchronous wait for its explicit synchronous API. | Do not move lifecycle-sensitive UI initialization blindly; remove only startup-path blocking work. |
| K. Logging/exceptions | Storage diagnostics are structured in-memory via `IStorageDiagnostics`; many services still use `Debug.WriteLine`; `DiagnosticsInfoService` builds sanitized copy text. There is no bounded rolling local log service. | Add a small local rolling writer with sanitized event fields, not a third-party framework. |
| L. Tests | Strong domain/service/data coverage: 398 tests currently pass. Existing coverage includes registry/search/favorites, storage/migrations, project/backup, settings, localization, update channels and packaging contracts. UI coverage is mostly contract tests; no unified startup timing or rolling-log tests yet. | Add focused registry capability, backup compatibility, settings normalization, channel and startup-stage tests. |

## Migration plan

1. **Tool Registry v2** — completed first slice: registry metadata now owns
   searchability, favorite capability and visibility; consumers honor those
   flags and constructor validation rejects invalid categories/page types.
2. **Data schema and migrations v2** — inventory every persisted boundary,
   retain existing paths, add only required migration steps, validate staged
   writes and preserve originals on failure.
3. **Import/export format v2** — retain v1 inspection/import, introduce an
   explicit v2 manifest contract and test future-version rejection and rollback.
4. **Settings service** — centralize keys/defaults/normalization while keeping
   the existing settings file and legacy fields readable.
5. **Distribution channels** — consolidate channel capabilities behind the
   existing identity detector without changing Store identity or update paths.
6. **Diagnostics** — add bounded local event logging and expose sanitized copy
   diagnostics; never log project contents or sensitive paths.
7. **Startup pipeline** — instrument stages, preserve first-frame behavior, and
   defer non-critical update/search/maintenance work.
8. **Tests and cleanup** — run full tests, Debug/Release x64 builds, packaged
   local validation, then produce a manual acceptance checklist.

Release boundary: this work stops before tag, GitHub Release, Store upload,
Store submission, listing edits and publication.

## Phase 2A checkpoint

- Project schema remains `3`; App Version remains separate.
- Unversioned project JSON is explicitly classified as legacy Schema 1.
- Existing `DataMigrationRunner` remains the sequential, UI-independent pipeline.
- Temporary writes and copied last-valid backups are parsed and validated before
  the formal file is replaced.
- Phase 2A test result: 400/400 passed in Debug x64 test execution.

Phase 2B is intentionally not started until the Debug/Release x64 build and
full-test checkpoint is complete.
