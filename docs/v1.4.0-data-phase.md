# v1.4.0 Foundation — Data Phase

## Phase 2A — Data Schema

- Current project schema: `3`.
- Unversioned project JSON: explicitly treated as legacy Schema 1.
- Migration chain: existing sequential 1→2→3 runner.
- Atomic write: temp file, flush, parse/version validation, then replace.
- Backup validation: copied last-valid backup is parsed before replacement.
- Future schema: rejected without changing the source file.

## Phase 2B — Import / Export Format v2

New manifests identify:

```json
{
  "format": "UrbanPlanToolbox Backup",
  "formatVersion": 2,
  "dataSchemaVersion": 3,
  "createdWith": "...",
  "createdAtUtc": "..."
}
```

Legacy manifests using `backupFormatVersion = 1` and
`exportedByAppVersion` remain readable through explicit legacy detection.
Future format versions and future data schema versions are rejected before
staging or LocalState replacement.

The existing ZIP layout and complete-restore semantics are unchanged. Import
continues to validate the archive, hashes, payloads, project schemas, and
working-folder references before creating the pre-import safety backup and
replacing official data.
